# DOM anchoring

The hard problem with element-pinned feedback is that the DOM you pinned to last week may not exist anymore. Class names get renamed, copy gets edited, list items get reordered, components get refactored. ccm-feedback's anchor system tries to keep your pin attached to "the same thing the reviewer meant" through reasonable amounts of churn.

This is best-effort, not magic. Big enough refactors will orphan pins, and that's expected.

## What gets stored at pin time

When the reviewer clicks an element, `src/dom/anchor.ts` captures everything it can about it:

| Signal           | Purpose                                                              |
| ---------------- | -------------------------------------------------------------------- |
| `cssSelector`    | Generated by [`@medv/finder`](https://github.com/antonmedv/finder). Optimized for stability — short, unique, prefers semantic attributes over nth-child chains. |
| `xpath`          | Direct DOM path. Survives some changes that break selectors.         |
| `elementId`      | If the element has an `id`, store it. Cheapest, most stable resolver. |
| `elementTag`     | Used as a coarse filter during fallback scans.                       |
| `textSnippet`    | First 500 chars of `textContent`. The best signal we have for "did we land on the same thing?" after a class rename. |
| `textPrefix`     | Adjacent text before the element. Helps disambiguate when many elements have similar text. |
| `textSuffix`     | Adjacent text after the element. Same.                               |
| `neighborText`   | Text from sibling/cousin elements. Resists same-tag scrambles within a parent. |
| `fingerprint`    | Tag-chain ancestry signature. Survives class/id changes; breaks on structural moves. |

Position is stored as **fractions of the anchor element's bounding box** (`xPct`, `yPct`, `wPct`, `hPct`). When the page re-renders at a different size, the rect rescales with the element.

## Resolution order

`resolveAnchor()` in `src/dom/resolver.ts` walks four levels, returning at the first one that passes text verification:

| Level | Strategy                                              | Confidence | Notes                                                   |
| ----- | ----------------------------------------------------- | ---------- | ------------------------------------------------------- |
| 1     | `getElementById` + tag check + fuzzy text match       | 1.00       | Cheapest. Fails fast if no `id`.                        |
| 2     | `querySelector(cssSelector)` + tag + text             | 0.95       | Fast. Breaks on class renames.                          |
| 3     | `document.evaluate(xpath)` + tag + text               | 0.90       | Survives some renames. Breaks on structural moves.      |
| 4     | Smart scan (fingerprint + text + prefix/suffix + neighbor) | up to 0.85 | Last resort. Walks up to 300 elements of the right tag. |

Text verification at every level prevents false positives — a CSS selector matching a different element with the same shape but different text won't be accepted.

## Smart scan scoring

When the structured selectors all fail, `smartScan()` collects every element with the same tag (capped at 300) and scores each one. Weights are **dynamic** — only signals that exist contribute, then the score is normalized over the active weight total:

| Signal              | Weight | Why                                                       |
| ------------------- | ------ | --------------------------------------------------------- |
| Text snippet match  | 40     | Most reliable for reordering / class churn.               |
| Fingerprint         | 20     | Structural similarity.                                    |
| Prefix + suffix     | 20     | Disambiguates between elements with similar text.         |
| Neighbor text       | 20     | Catches sibling-context matches.                          |

Threshold to accept: 0.4 normalized. Confidence is capped at 0.85 — smart scan is never declared "certain".

Early exit: if a candidate scores ≥ 0.85, the loop stops scanning further candidates.

## Failure modes

| Change                                                        | Outcome                                       |
| ------------------------------------------------------------- | --------------------------------------------- |
| Class names renamed                                           | CSS selector fails → XPath catches it.        |
| Copy edited slightly                                          | Fuzzy text match (`fuzzyIncludes`, threshold 0.3) tolerates small edits. |
| Element wrapped in a new container                            | XPath fails; smart scan catches via fingerprint + text. |
| List items reordered, same content                            | Text snippet wins — re-anchors to the right one. |
| Element deleted                                               | All four levels fail. Annotation is orphaned (returned as `null`; the marker isn't rendered). |
| Component split, text now spans two elements                  | Smart scan may match the parent or the wrong child. Confidence will be low. |

Orphaned annotations aren't deleted — they stay in the store so a future page version that restores the element will re-anchor them.

## What you can rely on

- An anchor that survives a class rename → almost always re-resolves
- An anchor that survives a small copy edit → almost always re-resolves
- An anchor whose target element was deleted → won't re-resolve, ever
- An anchor on a list of identical-looking items → fragile if the list reorders and the items have no distinguishing text

## What's intentionally not in scope

- **Multi-page anchors** — pins are scoped to `path` (normalized `location.pathname`). A pin on `/about` won't appear on `/contact`.
- **Cross-origin anchoring** — pins are stored against `url` for export, but resolution only runs on whatever page the widget is currently mounted on.
- **OT/CRDT semantics** — there's no merging, just last-write-wins (see [cloud-mode.md](cloud-mode.md#conflict-semantics)).

## Code map

- `src/dom/anchor.ts` — capture (`generateAnchor`) + percentage math (`rectToPercentages`)
- `src/dom/resolver.ts` — four-level resolver + scoring
- `src/dom/fingerprint.ts` — tag-chain signature
- `src/dom/fuzzy.ts` — `fuzzyIncludes`, `similarity` (string distance helpers)
- `src/dom/text-context.ts` — `adjacentText`, `neighborText`
- `src/dom/xpath.ts` — XPath generation
